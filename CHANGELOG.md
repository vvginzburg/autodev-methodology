# CHANGELOG методики AutoDev

## v3.2 — 2026-08-31

Повод: подготовка к запуску нового проекта. Перед стартом всплыли четыре вопроса,
которые методика нигде не требовала закрыть, хотя каждый из них меняет всю
разработку.

- **SPECIFICATION §0 «Рамка проекта»** — новый раздел перед всеми остальными:
  платформы, признак удачи одной фразой, живые данные и железо, отказы v1.
  Раздел нулевой, а не первый: перенумеровывать двенадцать существующих ради
  косметики дороже, чем оставить «ноль» как знак «до подробностей».
- **Фаза 1, шаг 1** — четыре вопроса задаются в брейншторме продукта, таблицей.
  Отказы v1 переехали из §11 в §0.4: два места для одного списка давали два
  источника правды.
- **Фаза 1, шаг 5** — барьер. Аудит начинает с §0; пустой пункт, заглушка
  шаблона или «не знаю» получают БЛОКИРУЮЩУЮ без обсуждения. Новый механизм
  не понадобился: цикл аудита уже не выпускает фазу с блокирующими дырами.
- **Правило закрытия пункта:** ответ человека ИЛИ явное «решай сам» с записью
  в DECISIONS.md. Молчание не закрывает — оно и было той дырой.

Источник урока: разговор о запуске нового проекта, 2026-08-31. Список вопросов
родился как совет «что прикинуть заранее» и оказался тем, чего методике
не хватало в обязательной части.

## v3.1 — 2026-08-31

Повод: разбор состава методики перед переносом в Codex. Источник урока — не
проект, а сам разбор: обнаружилось, что качество текста нигде не входит
в критерий готовности документа.

- **`elements-of-style` переведён из «полезно» в «обязательно»** (SKILL.md,
  «Зависимости»; принцип 12 «Не изобретай — компонуй»). Методика производит
  шесть документов, которые читает человек, и ни один из них не проверялся
  на читаемость.
- **Принцип 13 «Документ не готов, пока его не вычитали»**: SPECIFICATION,
  PLAN, DECISIONS, ARCHITECTURE, REPORT и CLAUDE.md проекта проходят через
  скил перед сдачей. Вычитка входит в критерий готовности наравне с полнотой.
- **Точки применения прописаны, а не подразумеваются**: фаза 1 шаг 4
  (SPECIFICATION) и шаг 8 (перед ревью человеком), фаза 4 пункт 6 (REPORT),
  строка в `templates/CLAUDE-template.md` — чтобы правило попадало в каждый
  новый проект автоматически.
- **Починено расхождение версий**: `SKILL.md` объявлял 3.0, `plugin.json` —
  2.3.0. Получатель плагина ставил бы «2.3».

**Ограничение, названное честно:** правила Strunk написаны для английского и
местами тянут в рубленую фразу. Для документов методики это выигрыш — их
читают на скорость и без автора рядом.

## v3.0 — 2026-08-31

Повод: разбор инструментария перед новым проектом. Три вывода, полученные
проверкой фактов, а не рассуждением.

- **`RRR.md` → `SPECIFICATION.md`** (31 упоминание, 12 файлов). Методика требует
  «никакого жаргона без расшифровки», а её главный документ был назван
  нерасшифровываемой аббревиатурой — расшифровки не нашлось ни в одном файле.
- **Фаза 0, шаг 6а «Заготовка проекта»**: `git init`, `.gitignore`, первый
  коммит, приватный репозиторий через `gh`. Дыра: методика проверяла наличие
  git и требовала `push` в смок-тесте, но репозиторий не создавала нигде.
- **Фаза 0, шаг 6б**: MCP-серверы не видят PATH из `~/.zshrc` — короткие имена
  (`uvx`, `npx`) прописывать абсолютным путём с явным `PATH` в `env`.
- **Фаза 1, шаг 5а «Решение о конвейере»** — обязательный, до составления плана.
  Умолчание: строим на autodev. Пять признаков берут отдельный инструмент,
  два — меняют конвейер. Отрицательное решение записывается наравне
  с положительным.
- **Принцип 11а**: сторонний фреймворк — решение, а не умолчание.
- **Задел «Главный инженер»** (SKILL.md): роль-прослойка между заказчиком
  и чужим фреймворком. Не вводится, пока фреймворка нет.

**Основание для умолчания — проверка журнала DocVault:** 24 задачи, два дня,
ноль вопросов человеку, вторая версия продукта через расширение ТЗ. GSD был
установлен за два дня до старта и не задействован ни разу (`.planning/`
в репозитории отсутствует). Конвейер autodev справился без фреймворка.

## v2.4 — 2026-08-30

Повод: в фазе 1 на «поиск решений» работал ровно один скил (brainstorming) —
это сбор требований, но не поиск решения и не проверка гипотез.

- **Шаг 3а «Инструменты поиска решения»** — три инструмента по триггеру:
  - **спайк**: код на выброс, отвечающий на ОДИН вопрос числом; папка
    `spikes/` в .gitignore; неподтверждённая гипотеза — успех, а не провал;
  - **панель вариантов**: три независимых агента с разной оптикой
    (простейшее / надёжное / быстрое до результата), человеку показывается
    таблица «чем платим», а не готовый вывод; отвергнутые варианты
    с причиной — в DECISIONS.md;
  - **скетч**: макет на выброс до написания SPECIFICATION §4, эталон в `docs/sketches/`.
- **Шаг 3б «Что помнит прошлое»** — поиск по прошлым разговорам и DECISIONS
  прошлых проектов перед написанием ТЗ.
- **Раздел «Экономика фазы 1»**: не звать инструменты впрок; признак
  необходимости один — решение влияет на план, и уверенности нет.
- Принцип 9а: дорогую развилку не решают первым пришедшим ответом.
