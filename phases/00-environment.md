# Фаза 0 — Проверка и подготовка окружения

Цель: методика самодостаточна — на чистой машине сама проверяет зависимости
и подтягивает недостающее. Прогоняется в начале КАЖДОГО проекта (идемпотентна,
на настроенной машине занимает минуту).

**Фаза 0 запускается ДВАЖДЫ**, если стек выбирается в проектировании:
- **0.A — до фазы 1**: универсальная часть (git, скилы, gh, факты о машине).
  Без неё нельзя даже проектировать.
- **0.B — после шага 2 фазы 1** (стек выбран): тулчейн стека.
  Без неё нельзя начинать фазу 2.

---

## 0.A Универсальное (до проектирования)

**Порядок шагов не произвольный.** Папка проекта и журнал проверки создаются
раньше тяжёлых проверок: установка плагина требует перезапуска сессии, и без
записанного состояния нить рвётся на пятой минуте первого проекта.

1. **Среда агента**: определить, где мы работаем (Claude Code / Codex CLI /
   другое) — от этого зависят пути конфигов и способ запуска сабагентов.
   См. reference/portability.md.
2. **git**: `git --version`. Нет (macOS предложит CLT) → человеку:
   «подтверди установку Command Line Tools в появившемся окне».

3. **Имя и место проекта.** Спросить у владельца рабочее имя (одно слово,
   переименуем позже, если захочется) и родительский каталог, если он ещё
   не задан рабочей папкой сессии. Без этих двух ответов дальше идти некуда:
   создавать папку вслепую нельзя.

4. **Один управляющий процесс — проверить ДО того, как что-то создавать.**
   В папке-кандидате не должно быть состояния чужого конвейера. Что именно
   искать — канонический список из четырёх признаков в phases/01-design.md,
   шаг 5а: папка планирования, чужой roadmap, файлы фаз, журнал состояния.
   Пусто — идём дальше. Нашлось — **остановиться и сообщить владельцу**,
   ничего не удаляя и ничего не создавая: проектом уже кто-то управлял,
   и решать, что с этим делать, ему (принцип 15).

5. **Заготовка проекта.** Папка проекта, `git init`, **базовый
   `.gitignore`** (мусор системы, файлы окружения, логи — стековые правила
   допишет 0.B, когда стек будет известен), первый коммит.

   Внутри папки создаётся **`autodev/`** — там живут все документы методики
   по этому проекту: SPECIFICATION, PLAN, DECISIONS, ESCALATIONS, ARCHITECTURE,
   REPORT, env-check.md, stack.md, pitfalls.md. Отдельная папка нужна, чтобы методика
   не сталкивалась с файлами, которые проект завёл до неё: у исследования,
   которое вёл AI, вполне может лежать свой `SPECIFICATION.md` в корне.

6. **CLAUDE.md — единственное исключение.** Он остаётся в корне проекта:
   среда читает его по фиксированному имени, переименовать или перенести
   нельзя. Поэтому файл **дополняется, а не перезаписывается**: если он уже
   есть, методика дописывает свой раздел запуска в конец и не трогает
   написанное до неё. Раздел указывает, что проект ведётся по autodev
   и документы лежат в `autodev/`.

7. **`autodev/env-check.md` — журнал проверки и точка возврата.** Таблица
   «зависимость → статус → что сделано», заполняется по ходу шагов 7–13.
   Нужна не для отчётности: любая установка ниже может потребовать перезапуска
   сессии, и после него новая сессия читает этот файл и продолжает с той
   строки, где остановились, а не начинает заново. Bootstrap проекта
   (`templates/CLAUDE-template.md`) знает это состояние и приводит сессию сюда.

8. **Скилы Superpowers** — методика на них ссылается. Проверка: доступны
   superpowers:brainstorming, writing-plans, subagent-driven-development,
   test-driven-development, verification-before-completion,
   systematic-debugging. Нет → установить
   (Claude Code: `claude plugin install superpowers@superpowers-marketplace`;
   Codex: через `/plugins` или из репозитория obra/superpowers). **После
   установки — перезапуск сессии; строку в env-check.md записать ДО него.**
9. **Сабагенты доступны**: в Claude Code — штатно; в Codex CLI требуется
   `[features] multi_agent = true` в `~/.codex/config.toml`. Без сабагентов
   методика не работает: рушится принцип «проверяет не тот, кто писал».
10. **context7 (MCP)** — доступ к актуальным докам. Ставить всегда: на шаге 0.A
   ещё неизвестно, будет ли стек знакомым, а решается это только в фазе 1.
   Без него исследователь и исполнители будут гадать по памяти модели, которая
   отстаёт. Точнее: без него исследователь и исполнители будут гадать по памяти
   модели. Нет → поставить до фазы 1.
11. **gh (GitHub CLI) + авторизация**: `gh auth status`. Нет бинаря → поставить
   релиз в ~/.local/bin (без brew/sudo, если их нет — проверить!).
   Не авторизован → человеку: «выполни `gh auth login` в терминале» (интерактив).
12. **git identity**: `git config user.name/user.email` — пусто → спросить
   человека один раз, записать глобально.
13. **Особенности машины**: есть ли brew/sudo (на машине Вадима — НЕТ, тулчейн
   в ~/.local); архитектура (arm64/x86); зафиксировать факты в CLAUDE.md проекта
   — тот раздел шаблона заполняется здесь, а не при создании файла на шаге 6.
14. **Сон**: способ держать машину бодрой (на macOS `caffeinate`) — проверить
   наличие.

15. **Приватный репозиторий**: из папки проекта
   `gh repo create <имя> --private --source=. --push`. Без `--source` команда
   уходит в интерактивный опрос и не привязывает локальный репозиторий.
   Идёт последним: до него нужен авторизованный gh (шаг 11).

**Выход 0.A**: `autodev/env-check.md` заполнен, всё зелёное, папка `autodev/`
и приватный репозиторий созданы — идём в фазу 1.

## 0.B Тулчейн выбранного стека (после шага 2 фазы 1)

Список пунктов пишет **Исследователь стека** — он же выбирал стек и знает,
что нужно. Обязательный минимум для ЛЮБОГО стека, без исключений:

| Проверка | Почему обязательна |
|---|---|
| компилятор/рантайм нужной версии | иначе нечем собирать |
| менеджер пакетов | и его кэш переживает офлайн-моменты |
| **раннер тестов + один зелёный тест-пустышка** | вся методика стоит на TDD; если тесты не запускаются, автономии не будет |
| команда сборки одной строкой | оркестратор и ревьюер вызывают её сотни раз |
| линтер/форматтер (если в стеке принят) | снимает шум в ревью |
| способ **живого запуска** (сервер/симулятор/CLI) | ревьюер обязан видеть работающий продукт, а не только зелёные тесты |
| установка **без brew/sudo**, если их нет на машине | см. 0.A п.13 |

**Дополнительно, если активирован Рецензент интерфейса и стек это позволяет**:
доступ к каталогу готовых интерфейсных компонентов. Он не заменяет обязательный
«способ живого запуска» из таблицы выше — тот остаётся, а каталог лишь даёт
роли откуда брать эталоны. Стек, для которого каталога не существует
(нативное приложение, сервер без интерфейса), — пункт пропускается: лишний
инструмент грузится в каждую сессию. Чем именно это закрывается в конкретной
среде — reference/portability.md.

**Стековый `.gitignore`.** База создана в 0.A шаге 4; здесь дописываются
правила стека — каталоги сборки, кэши менеджера пакетов, артефакты среды
разработки. Отдельным коммитом, до первой задачи: иначе мусор сборки попадёт
в репозиторий и будет мешать проверке `git status`, на которой стоит ревью.

Каждый установленный инструмент и каждая грабля при установке — немедленно
в `autodev/pitfalls.md` проекта.

**Выход 0.B**: всё зелёное ИЛИ явно отложенное с обоснованием, что оно не
блокирует фазы 2–3. Красное и блокирующее → дальше не идти.

## Приложение: пример 0.B для Apple-платформ (кейс DocVault)

1. **Xcode**: `xcodebuild -version`; симуляторы:
   `xcrun simctl list devices available | head`. Нет — человеку (App Store, долго).
2. **XcodeGen**: `xcodegen --version` или ~/.local/bin/xcodegen; нет →
   поставить релиз в ~/.local (+симлинк share — см. reference/pitfalls.md!).
3. **Аккаунт разработчика**: спросить человека, оформлен ли платный (если
   проекту нужны iCloud/устройства) — активация до 48 ч, запускать оформление
   немедленно, не блокируясь.

Приложения по другим стекам добавляются через ретро (фаза 5) по мере проектов.
