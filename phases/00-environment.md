# Фаза 0 — Проверка окружения Codex

Цель — подтвердить, что согласованный проект можно выполнить и проверить
на фактической машине. Канон адаптера — ../reference/portability.md.

## 0.A — До проектирования

1. Прочитать существующие AGENTS.md и точку входа проекта. Определить папку,
   текущую роль и ранее согласованный объём. Не спрашивать известное повторно.
   Не перезаписывать чужие документы. Признак чужого конвейера проверить по
   фазе 1, шагу 5а; одно лишь наличие дорожной карты ещё не доказывает, что
   другой конвейер сейчас управляет задачей: сначала выяснить по файлам.
2. Проверить git, текущую ветку, изменения и remote. При существующем проекте
   сохранить исходные изменения: для новых задач использовать отдельную чистую
   рабочую копию/ветку, если безопасно работать в текущей нельзя. Git identity
   использовать существующую; при отсутствии — настроить локально по известным
   данным или запросить недостающее. Не менять глобальные настройки.
3. Создать autodev/env-check.md: хост, путь, версии инструментов, результаты
   команд, доступные подагенты, возможности ревью, git/публикация, навыки,
   доступ к первоисточникам. Каждая строка: проверено / не требуется / блокирует
   конкретный шаг. Записать границу ближайшего продолжения.
4. Проверить фактический вызов свежего подагента ограниченной задачей чтения.
   Его успех не доказывает независимое ревью — полный цикл проверяет фаза 2.
   Если агенты недоступны, продолжать проектирование; разработку с независимым
   ревью не объявлять готовой к запуску.
5. Для нового репозитория создать локальный Git и первый коммит материалов
   процесса. Remote нужен только при согласованной публикации/резервировании.
   Локальный приёмочный пример вправе обходиться без GitHub и gh.
   Если remote нужен — проверить авторизацию и точную ветку; публикация только
   в уже согласованных границах, без force-push и без изменения видимости.
6. Добавить раздел AutoDev по templates/AGENTS-template.md в AGENTS.md проекта,
   сохранив существующие инструкции и распределение ролей. Заполнить путь к
   установленной методике. Наличие раздела не меняет роль каждого чата на
   оркестратора: роль определяется его конкретной задачей.
7. Подготовить обязательные исходники по ../reference/skills-integration.md:
   проверить Python 3.9+, архивы, конечные пути и фактическое чтение оригиналов.
   Сохранить версии и хеши в env-check. Для известного тестового профиля
   проверить нужные MCP; если стек ещё не выбран — завершить их выбор на 0.B.
   Наличие архива не означает применение навыка. Не подключать глобальные
   hooks и не менять исходники Claude.
8. Завести autodev/pitfalls.md и STATUS.md. Записать «фаза 0.A завершена» с
   доказательствами в env-check. Сохранять материалы процесса в Git.

Установка требуется лишь для обнаруженного препятствия согласованной работе.
Использовать доступные права, запросить недостающие средствами среды.
Не требовать от владельца технической настройки, которую агент может сделать.
Не копировать .claude/settings.json и не ослаблять sandbox/approval policy.

## 0.B — После выбора стека

1. Проверить конкретные компилятор/интерпретатор, зависимости и команды проекта.
   Существующее окружение сохранять; недостающее ставить в пределах задачи.
   Подтвердить применимые MCP реальными вызовами и зафиксировать версии/lockfile:
   Context7 при незнакомом стеке, каталог UI и браузер — по выбранному профилю.
   Установка на Pro учитывает готовность его инфраструктуры; Air не заменяет Pro.
2. Выполнить минимальную сборку и тест поведения (не тест наличия файла).
   На незнакомом стеке — ограниченный прототип проверки связки, результаты
   в autodev/stack.md. Уже существующие тесты запустить и отделить исходные
   ошибки от новых; не объявлять красное наследство зелёным.
3. Проверить необходимые платформы и доступ к данным на искусственных примерах.
   Недоступное устройство записать как ограничение, не обещать живую проверку.
4. Записать команды и результаты в env-check; отметить 0.B завершённой только
   при готовности сборки и проверки согласованного объёма. Дальше — фаза 2.

Сон и удалённая работа — отдельная инфраструктура. Не менять настройки питания
и не запускать бессрочные фоновые процессы при каждой сессии автоматически.
