# Фаза 3 — Автономная разработка

Конвейер на задачу (skill superpowers:subagent-driven-development).
Финальные строки отчётов и обязательные поля — roles/contracts.md.

```
оркестратор: бриф ──► исполнитель (TDD, свежий) ──► отчёт
                                                       │
                                                       ▼
  ## ГОТОВО ─────────► ревьюер (свежий, не писавший этот код)
  ## ЖДЁТ ───────────► триггер принципа 14: до ревьюера задача не доходит.
                       Откат незавершённого, [?] в PLAN, запись
                       в ESCALATIONS, следующая задача
  нет строки ────────► агент оборвался, не дойдя до конца. Оборвался
                       исполнитель — дерево откатывается по `git status`
                       (кроме `autodev/`), задача уходит новому исполнителю
                       целиком. Оборвался ревьюер или проверяющий — откатывать
                       нечего, работа исполнителя цела: вызывается новый
                       проверяющий по той же задаче

  ревьюер ──► ## ПРИНЯТО ──► проверки, привязанные к задаче (безопасность,
           │                  оценка AI — если активированы) ──► DECISIONS,
           │                  [x] в PLAN, commit, push ──► следующая задача
           └► ## ВОЗВРАТ ──► откат дерева к последнему коммиту, новый
                             исполнитель с замечаниями (макс 2, потом
                             оркестратор решает сам + DECISIONS — КРОМЕ
                             продуктовых развилок принципа 14: они идут
                             путём ЖДЁТ)

  Коммит стоит ПОСЛЕ проверок задачи намеренно: их возврат тогда ничего
  не откатывает — коммита ещё не было. Проверки раз в волну работают иначе,
  см. «Волновые проверки» ниже.
```

## Жизненный цикл задачи — единственный источник

**Правила этого раздела не пересказываются в других файлах.** Ядро ролей,
контракты, шаблоны плана и CLAUDE.md ссылаются сюда: правило, размноженное
по шести файлам, расходится с первой же правкой — это ловило три проверки
подряд.

## Правила смены

- Задачи строго последовательно (параллелить можно чтение/исследование,
  но не изменения кода).
- **Возврат проверки, привязанной к задаче, возвращает задачу в конвейер
  с начала**: новый исполнитель по замечанию проверяющего, затем снова ревьюер,
  затем снова та же проверка. Она идёт после ревью и не заменяет его.
- **Коммит и push — после всех проверок, привязанных к задаче.** Вердикт
  ревьюера открывает проверки безопасности и оценки AI, если они активированы;
  задача уходит в репозиторий, только когда зелены все. До этого момента она
  живёт в рабочем дереве, и любой возврат обходится откатом, а не переписыванием
  истории.
- **Файлы процесса коммитятся сразу, как записаны.** Запись в ESCALATIONS,
  пометка `[?]` или `[x]` в PLAN, строка в DECISIONS — отдельным коммитом
  «процесс: <что записано>», немедленно. Две причины. Первая: незакоммиченная
  запись об эскалации погибнет при первом же откате — а откат случается часто.
  Вторая: ревьюер проверяет рамки задачи через `git status`, и чужие
  изменённые файлы в дереве заставляют его вернуть задачу ни за что.
- **Откат дерева не трогает папку `autodev/`.** Он возвращает код, а не
  состояние процесса: `git restore` и удаление новых файлов применяются
  к рабочим файлам задачи, документы методики остаются как есть — они уже
  закоммичены предыдущим правилом.
- **Откат дерева обязателен на каждом пути, где задача уходит переделываться:**
  `## ВОЗВРАТ`, `## ЖДЁТ`, обрыв без финальной строки. При возврате и ЖДЁТ список
  файлов берётся из отчёта; при обрыве отчёта нет — оркестратор откатывает
  по `git status`, то есть всё, что появилось в дереве с последнего коммита.
  Без этого следующий исполнитель садится на чужой недоделанный код, ревьюер
  видит чужие файлы в рамках задачи и возвращает её ни за что.
- **`## ВОЗВРАТ` откатывает рабочее дерево** — `git restore` по изменённым
  файлам задачи и удаление созданных ею новых. Новый исполнитель садится
  на чистое наследство: иначе он получает чужой недоделанный код и правило
  «наследство зелёное» перестаёт что-либо значить.
- **После двух возвратов оркестратор решает спор, а не закрывает задачу.**
  Дерево к этому моменту откачено дважды, кода в нём нет — принять тут нечего.
  Оркестратор разбирает предмет спора (обычно ревьюер и исполнитель понимают
  требование по-разному), пишет решение в DECISIONS и отдаёт задачу **третьему
  исполнителю**, вложив это решение в бриф отдельной строкой. Ревьюер третьего
  круга проверяет уже по решённому вопросу и по нему не возвращает. Правило
  ограничивает не число попыток, а число кругов спора: спорить об одном и том же
  дважды — предел.
- Каждая итерация начинается с прогона тестов (наследство зелёное).
- Экономия прогонов: полный набор — на приёмке задачи ревьюером; исполнитель
  между red/green может гонять только затронутые сьюты.
- **Волновые проверки** — интеграционный ревьюер и Рецензент интерфейса (если
  активированы) — смотрят на задачи, уже принятые и запушенные. Их `## ВОЗВРАТ`
  **ничего не откатывает**: оркестратор заводит в текущую волну задачу-исправление
  со ссылкой на замечание, а принятые задачи остаются принятыми. Переписывать
  историю ради волнового замечания дороже, чем исправить следующей задачей.
- Раз в волну — интеграционный ревьюер (если активирован): сквозной сценарий +
  живой запуск платформ.
- Задача трогала защищаемое из SPECIFICATION §13 (если активирован Рецензент
  безопасности): после ревьюера — независимая проверка, что мера на месте
  и работает. Регрессия защиты = ВОЗВРАТ, и правило «после двух возвратов
  оркестратор решает сам» на неё тоже не действует: снижение защиты — решение
  владельца через ESCALATIONS.
  **Выход, когда починка не помогает:** вторая подряд регрессия по одной задаче
  означает, что мера и требование несовместимы текущим подходом. Оркестратор
  заводит запись в ESCALATIONS («мера §13 не держится, вот что пробовали,
  варианты: изменить требование / сменить подход / принять риск»), ставит задаче
  `[?]` и берёт следующую. Порядок тот же, что у красной оценки AI.
- Раз в волну, если активирован Рецензент интерфейса: сверка сделанного
  с контрактом `autodev/ui.md`, расхождения списком.
- Задача трогала AI-компонент (если активирован Инженер оценки AI): после
  ревьюера — независимый прогон сетки оценки, результат в `autodev/eval.md`.
  Числа ниже порога или хуже прошлого прогона = ВОЗВРАТ, наравне с красными
  тестами. Оценивает не тот агент, который писал компонент. Правило «после двух
  возвратов оркестратор решает сам» здесь не действует: красную оценку закрывает
  только зелёный прогон либо изменение порога владельцем.
  **Выход, когда исправления не помогают:** второй красный прогон подряд по одной
  задаче означает, что порог недостижим текущим подходом. Оркестратор по
  собственной находке заводит запись в ESCALATIONS («порог §5 недостижим, вот
  цифры прогонов, варианты: снизить порог / сменить подход / отказаться
  от функции»), откатывает дерево, ставит задаче `[?]` и берёт следующую. Без этого выхода задача
  не становится ни принятой, ни отложенной, и граница волны недостижима.
- **Лимит смены или конец контекста.** Коммитится только то, что прошло
  проверку: задача в работе откатывается, как при возврате, и остаётся `[ ]` —
  непроверенный код в репозиторий не уходит, иначе следующая смена начинается
  с наследства неизвестного качества. Файлы процесса уже закоммичены. Дальше
  `autodev/REPORT.md` с точкой продолжения; новая сессия в папке проекта
  продолжает по CLAUDE.md bootstrap.
- Зависшего сабагента будить сообщением (возобновление сохраняет его контекст);
  пересоздавать — только между задачами.
- Человека НЕ спрашивать по техническим и обратимым вопросам: пробел в ТЗ →
  решение + autodev/DECISIONS.md.
- **Сработал триггер эскалации** (границы продукта, безопасность, существенные
  расходы, смысл пользовательского обещания — принцип 14). Порядок действий,
  один на все случаи:

  1. **Исполнитель** останавливает работу над задачей сразу, как понял, что
     развилка продуктовая, — не доделывает её ни на одном из вариантов
     и не выбирает сам. Отчёт заканчивается строкой `## ЖДЁТ` и содержит
     четыре графы: суть развилки, оба исхода, что уже успел написать
     и **какие файлы затронул** — по ним пойдёт откат (шаг 2).
  2. **Оркестратор откатывает незавершённое** — рабочее дерево возвращается
     к последнему коммиту: `git restore` по изменённым файлам задачи **и**
     удаление созданных ею новых файлов (`git restore` неотслеживаемые
     не трогает, а задача чаще всего создала именно их — потому графа «Файлы»
     в отчёте обязательна). Правило «наследство
     зелёное» и проверка ревьюером `git status` держатся только на чистом
     дереве, поэтому частичный код не сохраняется: задача будет сделана заново,
     когда владелец ответит.
  3. **Оркестратор пишет запись** в `autodev/ESCALATIONS.md` на языке
     последствий и ставит в `autodev/PLAN.md` пометку `[?]` **каждой** задаче,
     которую эта развилка держит, — и той, что упёрлась, и тем, у кого она
     в «Зависимостях».
  4. Берётся следующая задача без `[?]`. До ревьюера задача с `[?]` не доходит,
     принятой не считается и в PLAN не закрывается.

  **Источник правды — пометки `[?]` в PLAN.** Поле «Задачи» в записи
  ESCALATIONS их дублирует для удобства чтения; при расхождении верна PLAN.
- **Граница волны — когда каждая задача волны либо принята, либо помечена
  `[?]`.** В этот момент оркестратор вручает владельцу пакет: все открытые
  записи ESCALATIONS одним разговором. Досрочно — только если `[?]` получили
  все оставшиеся задачи и работать не над чем.
- **Владелец ответил.** Оркестратор записывает решение в `autodev/DECISIONS.md`
  с пометкой «решение владельца», переносит запись в раздел «Закрытые»
  ESCALATIONS, снимает `[?]` — и задачи возвращаются в очередь обычным
  конвейером. Три исхода требуют разного, и все три оформляются одинаково
  строго:

  | Что решил владелец | Куда это записывается |
  |---|---|
  | продолжаем так-то (развилка принципа 14) | DECISIONS; задача делается заново по решению |
  | требование меняется — снизить порог, ослабить меру защиты, принять риск | **правка SPECIFICATION** (§5, §13 — смотря что менялось) плюс DECISIONS со старым и новым значением; без правки ТЗ выход фазы 3 останется недостижим, потому что сверяется он с ТЗ |
  | функция не нужна | задача помечается `[—] отменена решением владельца`, строка уходит в SPECIFICATION §11 «не входит в v1»; отменённая задача не мешает выходу фазы наравне с принятой |
- **Владелец не отвечает, а задач без `[?]` не осталось.** Оркестратор не ждёт
  в сессии: прогоняет тесты, пишет `autodev/REPORT.md` с точкой продолжения
  и завершает смену. Следующая сессия по bootstrap видит открытые эскалации
  и, если ответа всё ещё нет, завершается тем же образом.

  **Это легальное состояние, а не тупик.** Фаза 3 приостановлена, и приостановка
  длится ровно столько, сколько владелец не отвечает; методика его не торопит
  и не решает за него. Что делает оркестратор в каждой такой сессии, кроме
  завершения: проверяет, не появился ли ответ; убеждается, что тесты зелёные;
  обновляет точку продолжения, если что-то изменилось снаружи (обновилась
  зависимость, истёк сертификат). Ни одной задачи он при этом не берёт —
  работа над `[?]` запрещена.

## Гигиена

- Отчёты ревьюеров «на заметку» → хвосты в DECISIONS с адресатом
  (какая будущая задача обязана закрыть).
- Инфраструктурные грабли → autodev/pitfalls.md проекта немедленно
  (следующий сабагент не должен наступать снова).
- Прогресс человеку виден без вопросов: git log + галочки autodev/PLAN.md.

## Выход фазы
Все задачи PLAN приняты или отменены решением владельца — **`[?]`
не осталось ни одной**: фаза 3 не заканчивается с открытой эскалацией. Если активирован Рецензент безопасности — все меры
из SPECIFICATION §13 подтверждены; вход фазы 4 требует того же, и расходиться
эти два списка не должны. Владелец ответил, задачи достроены, и только после этого
идёт финальная задача. Если активирован Инженер оценки AI — последний прогон
`autodev/eval.md` зелёный: фаза 3 не заканчивается с красной оценкой.
Финальная задача прогнала все критерии приёмки SPECIFICATION §10.1 —
проверяемые автоматически; §10.2 (физический мир) выполняет человек на фазе 4,
и в объём агента он не входит
одним свежим заходом (skill superpowers:verification-before-completion);
autodev/REPORT.md с галереей скриншотов и инструкцией приёмки.
