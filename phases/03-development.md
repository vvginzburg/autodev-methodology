# Фаза 3 — Автономная разработка

Это единственный источник жизненного цикла задачи. Роли и шаблоны ссылаются
сюда; граница решений — принцип 14 SKILL.md, поля отчётов — roles/contracts.md.

## До задачи

1. Прочитать PLAN, SPECIFICATION, DECISIONS, ESCALATIONS и состояние среды.
   Взять первую доступную задачу по зависимостям. `[?]` не брать, пока нет
   подтверждённого ответа; `[—]` — отменена владельцем, `[x]` — принята.
2. Проверить исходное состояние Git и наследуемые тесты. Сохранить исходный
   commit, список изменений и область задачи в autodev/task-baseline.md.
   Чужие/неизвестные изменения не считать результатом текущего исполнителя.
   При пересечении использовать изолированную чистую рабочую копию или
   сохранить доказанную исходную версию. Небезопасную общую папку не очищать.
3. Записать STATUS: задача, шаг «исполнитель», последнее событие и время.
4. Дать свежему исполнителю ограниченный бриф из roles/core.md: требования,
   границы файлов, критерии, полномочия §0.6, конфигурация, контракт отчёта,
   указатели на stack/pitfalls/bug-patterns, запрет коммитов и правки управляющих PLAN/DECISIONS/ESCALATIONS/STATUS. Явно порученные артефакты ARCHITECTURE/REPORT исполнитель пишет по брифу; это не запрещено.

Код меняет один исполнитель за раз. Чтение и исследования можно выполнять
параллельно. Настоящий независимый ревьюер обязателен; невозможность его
запустить — препятствие, а не разрешение принять собственный результат.

## Цикл и обязательные действия на каждом исходе

| Событие | Действия оркестратора |
|---|---|
| Исполнитель ГОТОВО | проверить полноту отчёта; STATUS «ревью»; запустить свежего ревьюера, не писавшего код |
| Исполнитель ЖДЁТ | проверить основание по принципу 14; безопасно вернуть изменения задачи; записать ESCALATIONS, пометить зависимые задачи [?], записать STATUS; сохранить процесс и взять независимую задачу |
| Обрыв исполнителя без финальной строки | сверить живой статус агента; при подтверждённом обрыве безопасно вернуть только его изменения к исходной точке, записать STATUS; передать задачу свежему исполнителю |
| Обрыв ревьюера | сохранить работу исполнителя; STATUS «ревью прервано»; вызвать другого независимого ревьюера |
| Ревьюер ВОЗВРАТ | сохранить замечания; STATUS «возврат»; безопасно вернуть изменения задачи; новый исполнитель с замечаниями, затем новое ревью |
| Ревьюер ПРИНЯТО | выполнить дополнительные проверки задачи, если активированы безопасность/оценка AI; до их окончания задача не принята |
| Все проверки задачи приняты | перенести решения в DECISIONS, отметить [x] в PLAN, записать STATUS «задача принята»; коммит проверенного кода и материалов процесса; push только если согласован; перейти к следующей доступной задаче |
| Дополнительная проверка ВОЗВРАТ | тот же возврат с новым исполнителем, ревьюером и повторением этой проверки; записать STATUS |

Наличие финальной строки не доказывает качество: ревьюер проверяет факты,
а оркестратор — полноту нужных проверок. Агент не завершает отчёт до результата
своих длительных команд. Пока агент работает, ожидать его штатным инструментом;
не перезапускать живую роль только из-за отсутствия нового текста.

## Безопасный возврат и Git

Возврат означает восстановление **исходного состояния конкретной задачи**,
не очистку всего дерева. Сопоставить task-baseline, git diff и список файлов
исполнителя. В чистой изолированной копии можно вернуть перечисленные файлы
к исходному commit и удалить только доказанно созданные этой задачей файлы.
Существовавшее до задачи, изменения других ролей/владельца, неизвестные файлы,
индекс Git и `autodev/` не затирать. `git status` сам по себе не доказывает
авторство. При сомнении сохранить частичную работу отдельно и продолжить в
чистой изоляции; разрушительную очистку не делать.

Процесс сохраняется на каждом переходе таблицы: PLAN, DECISIONS, ESCALATIONS,
STATUS и ссылка на отчёты. Можно одним атомарным коммитом перехода; во время
непринятого кода добавлять только названные файлы процесса, не `git add .`.
Для принятой задачи допустим общий коммит проверенного кода и процесса.
Непроверенный код не коммитить в ветку принятого результата. Перед коммитом
посмотреть staged diff; чужое не включать. Ошибка commit/push отмечается
отдельно: файл на диске, локальный commit и удалённая копия — разные состояния.
Непрошедший push не отменяет локальную приёмку и не оправдывает force-push.

## Возвраты и проверки

После двух возвратов по одному спору оркестратор разбирает требование,
записывает решение в DECISIONS и передаёт новому исполнителю. Он не объявляет
задачу принятой без кода/ревью. Граница полномочий принципа 14 сохраняется.

Каждая итерация проверяет наследство; между red/green исполнитель запускает
затронутые проверки, ревьюер — достаточный набор регрессий. Без изменения или
нерешённой причины зелёные проверки бесконечно не повторять.

Если активирована безопасность и задача затронула меры SPECIFICATION §13 —
независимая проверка после ревью. Если затронут AI-компонент — независимый
прогон eval.md, сравнение с согласованными порогами и предыдущим результатом.
Снижение защиты или порога качества агентом запрещено. После двух неудач одного
подхода исследовать разрешённую альтернативу. Если приемлемого пути нет —
ESCALATIONS по принципу 14 с фактами, варианты изменения продукта владельцу.
Не считать второй неудачный тест сам по себе доказательством невозможности.

На границе волны — интеграционная/визуальная проверка, если роли активированы.
Возврат такой проверки не переписывает историю принятых задач: добавить
задачу исправления в текущую волну с причиной, провести полный цикл.

## Эскалации и возобновление

1. Сверить реальную границу §0.6/DECISIONS, а не только слово «продуктовая».
   Делегированное обратимое решение — DECISIONS и продолжение.
2. Необходимый вопрос — ESCALATIONS по шаблону, [?] у упёршейся и всех её
   зависимых задач, STATUS с подтверждённым событием. Не реализовывать
   зарезервированный выбор даже как временный вариант.
3. Продолжать независимые задачи. Граница волны: задачи либо приняты, либо
   ожидают, либо отменены. Предъявить пакет вопросов с вариантами, последствиями
   и рекомендацией; раньше — когда полезной независимой работы больше нет.
   Вопрос продублировать видимым блоком ВОПРОС ВЛАДЕЛЬЦУ в REPORT и сообщении.
4. Ответ получен: записать его как решение владельца в DECISIONS, согласованное
   изменение — в ТЗ и сверку §14; закрыть эскалацию, снять [?] у зависимых задач,
   обновить STATUS, продолжить с первой доступной задачи без нового согласования.
   Владелец отменил функцию — [—] в PLAN, отказ в SPECIFICATION §11.
5. Ответа нет и независимого нет: сохранить REPORT с точкой продолжения,
   STATUS «жду ответа владельца», коммит процесса; завершить ход конкретным
   вопросом. Молчание не является ответом. На новой сессии проверить ответ,
   не повторять без причины все тесты и не брать заблокированное.

## Наблюдаемость и конец смены

STATUS содержит четыре строки: Этап; Последнее событие (что подтверждено
и когда); Состояние; Обновлено (время с часовым поясом). Состояния: работаю,
жду ответа владельца, ошибка, не могу продолжить, завершено. Последнее нужно
для реально завершённой смены/этапа: не оставлять «работаю» после остановки.
Запись обязательна на каждом переходе таблицы и при смене состояния.
В длинной работе давать краткие сообщения по существу в канале среды.
Не придумывать процент готовности или время завершения без оснований.

При исчерпании контекста/лимите сохранить принятый результат; для незавершённого
использовать безопасный возврат выше, оставив задачу незакрытой. REPORT:
исходная точка, что проверено, что не закончено, точный следующий шаг.
STATUS — итоговое состояние с причиной остановки. Следующая сессия идёт
по AGENTS bootstrap, не по предположению «есть PLAN — всё разрешено».

## Выход фазы

Все задачи приняты либо отменены владельцем; нет [?] и открытых эскалаций;
активированные проверки безопасности и AI зелёные. Предпоследняя задача —
ARCHITECTURE; финальная — свежая проверка всех автоматических критериев
SPECIFICATION §10.1 и REPORT с доказательствами и инструкцией приёмки.
Человеческую §10.2 не засчитывать автоматически. Записать завершение фазы 3
в env-check/STATUS; затем предъявить готовый результат на фазе 4.
