# AutoDev — методика автономной агентной разработки

Версия 4.0 · выработана на проекте DocVault (2026-07-06/07) · развивается: см. CHANGELOG.md

**Человеку**: полный рассказ, как методика работает, — [README.md](README.md).
Этот файл — токен-экономный вход для AI.

## Резюме для человека (1 минута)

Человек **долго проектирует** и один раз отвечает на все вопросы. AI **автономно строит**
и не беспокоит человека техникой: обратимые вопросы без ответа в ТЗ решаются
самостоятельно и записываются. Развилки, меняющие сам продукт, копятся в пакет
и вручаются владельцу на границе волны — принцип 14.
Каждую задачу делает свежий агент-исполнитель через TDD, принимает — **независимый
агент-ревьюер**, никогда не тот, кто писал. Каждая принятая задача = git-коммит.
Человек возвращается на **приёмку** (проверяет руками только то, что существует
в физическом мире: камера, живые устройства, реальные данные) и на **ретро**
(что улучшить в методике). Найденные на приёмке баги чинятся тем же конвейером.

Результат DocVault-калибровки: 16 задач + 4 багфикса за ~2 суток, 76 тестов × 2
платформы, участие человека ≈ 1 час на приёмке.

## Несущие принципы (выстраданы, не менять без ретро-обоснования)

1. **Проверяет не тот, кто писал.** Самопроверка исполнителя систематически завышает
   готовность. Ревьюер перепроверяет фактами: сам гоняет тесты, сам читает первоисточники.
2. **Рабочие агенты — свежие, консультанты — долгоживущие.** Свежий контекст на задачу =
   незамыленный глаз + линейная (не квадратичная) стоимость токенов. Повторяющееся знание
   живёт в файлах (CLAUDE.md проекта, autodev/stack.md, autodev/pitfalls.md;
общие грабли окружения — в reference/pitfalls.md методики), а не в брифах.
3. **Вопросы не блокируют.** Нет ответа в SPECIFICATION → разумное инженерное решение → запись
   в autodev/DECISIONS.md (дата, вопрос, решение, почему). Человек читает файл после, за 10 минут.
   Граница этого правила — принцип 14: оно про технические и обратимые решения.
4. **Коммит на принятую задачу.** Git — единственная надёжная память процесса: переживает
   обрывы, лимиты, закрытые крышки. Прогресс = git log, а не самоотчёты.
5. **Первая итерация — только план.** Дальше задачи берутся из autodev/PLAN.md, приоритеты
   не переосмысляются (иначе осцилляция). План живой: правки — с причиной в коммите.
6. **Граница автоматизации проходит по физическому миру.** Всё, что проверяемо программно,
   проверяет AI (фейки железа за протоколами — см. roles/). Человеку остаётся камера,
   кабель, живой аккаунт — и это не «тестирование», а финальный сенсор реальности.
7. **Изолируй железо за протоколом с первого дня.** Две реализации сразу: настоящая
   и фейковая; выбор в composition root. Отдельного этапа «подключить настоящее» нет.
8. **Стек — решение человека, всё остальное про стек — работа AI.** Выбор
   технологии необратим посреди ночи, поэтому он один из четырёх пунктов фазы 1, где
   голос человека обязателен. Но обосновать выбор, изучить доки и написать
   выжимку обязан AI (роль Исследователя), а не человек.
9. **Полнота ТЗ проверяется свежим агентом, а не ощущением.** Пока независимый
   аудит SPECIFICATION находит БЛОКИРУЮЩИЕ дыры, разработку не начинать. «Мне кажется,
   мы всё обсудили» — не критерий.
9а. **Дорогую развилку не решают первым пришедшим ответом.** Одно решение
   выглядит убедительно всегда — сравнивать не с чем. Три независимых
   варианта показывают цену выбора; гипотезу проверяет спайк, а не спор.
10. **Методика не прирастает к среде.** Никаких путей конкретного агента
   и ничего исполняемого в теле фаз — см. reference/portability.md.
11а. **Сторонний фреймворк — решение владельца, а не умолчание.** Строим
   на autodev, пока не сработал именованный признак (фаза 1, шаг 5а). Признаки
   проекта закрываются ролями методики, а не чужими скилами. Конвейер меняется
   только по двум признакам, только до плана и только по слову владельца —
   AI такое решение не принимает. Отрицательное решение записывается наравне
   с положительным.
12. **Не изобретай — компонуй.** Методика ссылается на установленные скилы
   (superpowers:brainstorming, writing-plans, subagent-driven-development,
   test-driven-development, verification-before-completion;
   elements-of-style:writing-clearly-and-concisely) и добавляет слой оркестрации,
   которого в них нет.
13. **Документ не готов, пока его не вычитали.** Любой документ, который читает
   человек — SPECIFICATION, PLAN, DECISIONS, ESCALATIONS, ARCHITECTURE, REPORT, CLAUDE.md
   проекта, — перед сдачей проходит через elements-of-style. Причина не
   косметическая: мутная строка в ТЗ стоит ветки неправильной разработки —
   исполнитель читает её ночью, и спросить некого. Вычитка входит в критерий
   готовности документа наравне с полнотой.

14. **Автономия — на обратимом.** Технические и обратимые решения AI принимает
   сам. Решения, меняющие продукт, собираются в пакет и передаются владельцу.
   Четыре действующих триггера — вопрос эскалируется, если он меняет:
   **границы продукта**, **безопасность**, **существенные расходы**,
   **смысл пользовательского обещания** (что продукт обещает человеку
   и что тот вправе ожидать). Ещё два кандидата — персональные данные,
   согласие и раскрытие — отложены до первого проверочного проекта
   и ждут в OPEN-QUESTIONS.md.

   Эскалация НЕ останавливает работу: вопрос уходит в autodev/ESCALATIONS.md,
   задача помечается, агент берёт следующую. Пакет вручается на границе волны —
   раньше только если уперлось всё оставшееся.

   **Ноль вопросов человеку — не цель.** Цель — ноль технических вопросов
   при нуле пропущенных продуктовых. Пустой ESCALATIONS.md в проекте, который
   трогает деньги или чужие данные, — не достижение, а повод перепроверить.

15. **Единственный владелец жизненного цикла.** Проект, запущенный по autodev,
   ведёт autodev — и только он. Чужой фреймворк внутри этого проекта не заводит
   собственный план, состояние, этапы, управляющих агентов, проверки переходов
   и порядок работы с git. Конкретно запрещено: инициализировать чужой конвейер
   внутри проекта; заводить его хранилище состояния; запускать его команды —
   создание проекта, roadmap, фазы, плана, исполнение, проверку, сдачу;
   подключать его capabilities, hooks и gates; отдавать ему управление агентами;
   позволять ему делать коммиты и ветки. Как узнаётся чужое состояние — канон
   в phases/01-design.md, шаг 5а.

   **Методика не становится capability чужого фреймворка.** Модульность
   современных фреймворков делает это технически привлекательным, но тогда
   владельцем процесса становится он, а не autodev, — и принцип отменяет
   сам себя.

   **Чужие скилы — запрещено по умолчанию.** Нельзя звать скил потому, что его
   название похоже на нужную функцию: он может оказаться входом в чужой конвейер.
   Разрешение даётся поимённо и только после проверки (фаза 1, шаг 5а).

   Чужой фреймворк при этом может стоять на машине и использоваться
   в проектах, где autodev не активирован. Запрет — про один проект,
   не про машину.

**Задел на будущее — роль «Главный инженер».** Нужна ТОЛЬКО в случае ЗАМЕНЫ
конвейера (шаг 5а): проект ведёт сторонний фреймворк, а методика остаётся сводом
правил. Внутри проекта на autodev такого состояния не бывает — два конвейера
рядом запрещены. Три функции: перевод вопросов фреймворка с языка
разработчика на язык результата и обратно; фильтр эскалаций (фреймворк будит
разработчика — инженер решает сам и пишет в DECISIONS, либо выносит человеку
укрупнённо); охрана границы приёмки. Без фреймворка эти функции выполняет
оркестратор, отдельная роль не выделяется — правило второго раза.

## Роли

Ядро (всегда): **оркестратор + исполнитель + ревьюер** — [roles/core.md](roles/core.md).
Признак «продукт содержит AI-компонент, который нельзя проверить равенством»
(LLM, embeddings, семантический поиск, ранжирование, классификация, агентное
поведение) активирует **Инженера оценки AI** — на фазе 1, до плана.
Первый кандидат с полки в новом проекте — **Исследователь стека и решений**
(обязателен, если стек не выбран или незнаком).
Полка (по признакам проекта или «правилу второго раза»): [roles/catalog.md](roles/catalog.md).
Правило второго раза: оркестратор делает работу руками второй раз подряд → выделяет роль.

**Контракт роли — [roles/contracts.md](roles/contracts.md).** Инструкция говорит,
ЧТО делает роль; контракт — чем она обязана закончить отчёт и что в нём обязано
быть. Финальная строка одна из четырёх: `## ГОТОВО`, `## ПРИНЯТО`, `## ВОЗВРАТ`,
`## ЖДЁТ`; набор обязательных полей зависит от неё.

## Файлы проекта (шаблоны в templates/)

Все документы методики живут в папке **`autodev/`** в корне проекта. Так они
не сталкиваются с файлами, которые проект завёл до методики: у исследования,
которое вёл AI, вполне может быть свой `SPECIFICATION.md` в корне.
Исключение одно — **`CLAUDE.md` остаётся в корне**: среда читает его
по фиксированному имени. Если он уже есть, методика дописывает свой раздел
в конец и не трогает написанное до неё.

| Файл | Назначение | Шаблон |
|---|---|---|
| autodev/SPECIFICATION.md | §0 рамка (платформы, признак удачи, живые данные, отказы v1) — закрывается первой; далее результат, критерии приёмки (авто + человеческие), решения, грабли | templates/SPECIFICATION-template.md |
| autodev/PLAN.md | задачи волнами: Files/Produces/Зависимости/Критерий готовности | templates/PLAN-template.md |

| autodev/ESCALATIONS.md | пакет решений для владельца — принцип 14 | templates/ESCALATIONS-template.md |

## Зависимости (проверяет фаза 0)

Обязательно: среда с поддержкой скилов и сабагентов (Claude Code, Codex CLI —
см. reference/portability.md); git; плагин Superpowers (используются скилы
brainstorming, writing-plans, subagent-driven-development,
test-driven-development, verification-before-completion, systematic-debugging); gh авторизованный;
context7 (MCP) — критичен, если стек незнаком; плагин elements-of-style —
каждый документ для человека проходит через него перед сдачей (принцип 13).
Полезно, не обязательно: episodic-memory (поиск по прошлым сессиям — фаза 1,
шаг 3б).
По стеку (фаза 0.B, то есть ПОСЛЕ выбора стека на шаге 2 — на шаге 1
о технологиях не говорят): shadcn (MCP) — каталог готовых интерфейсных
компонентов и блоков; playwright (MCP) — проверка живого интерфейса. Оба нужны,
только если активирована роль «Рецензент интерфейса» И стек веб-совместимый;
для нативного приложения или сервера без интерфейса не ставятся.
По признаку из шага 1: serena (семантический анализ кода) — ставить в проект,
не глобально.
По типу проекта: см. phases/00-environment.md. На чистой машине НЕ предполагать
ничего — фаза 0 проверяет и ставит.

## Быстрый старт нового проекта

0. Прогони фазу 0.A (phases/00-environment.md) — универсальное окружение.
1. Прочитай phases/01-design.md → диалог с человеком-заказчиком (без жаргона) →
   выбор стека Исследователем → autodev/SPECIFICATION.md + autodev/PLAN.md + CLAUDE.md + autodev/stack.md.
   Не выходить из фазы, пока аудит полноты возвращает БЛОКИРУЮЩИЕ дыры.
   После выбора стека — вернуться в фазу 0.B за тулчейном.
2. Фаза 2 обязательна и заканчивается СМОК-ТЕСТОМ: пустая задача проходит полный цикл
   (агент → сборка → тест → коммит) без единого вопроса человеку. Не зелёный смок —
   не начинай разработку.
3. Разработка по phases/03. Приёмка по phases/04. Ретро по phases/05 — с коммитом сюда.
