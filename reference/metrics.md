# Метрики эффективности методики

Считать на каждом проекте, сравнивать с базовой линией. Цель развития
методики — улучшать эти числа, а не ощущения.

| Метрика | Как считать | База (DocVault, v2.0) |
|---|---|---|
| Принято с первого раза | задачи без возврата / все | 18/20 (2 возврата, оба процессные) |
| Баги приёмки / 10 задач | находки человека ÷ задачи × 10 | 2.0 (4 на 20) |
| Минуты человека | проектирование + приёмка + ретро | ~180 + ~60 + ~60 |
| Технические вопросы к человеку | шт. | 0 (цель — всегда 0) |
| Эскалации владельцу | записи в ESCALATIONS.md | 0 (цель НЕ ноль — см. ниже) |
| Пропущенные продуктовые решения | найдено на приёмке/ретро: AI решил сам то, что должен был эскалировать | 0 (цель — всегда 0) |
| Токены / задача | по отчётам сабагентов | ~100–170 тыс. |
| Доля потенциально параллельных задач | помечены в PLAN, не имеют общих файлов ÷ все задачи | не измерялась (OPEN-QUESTIONS Q-1) |
| Обрывы без потерь | обрыв смены с потерей > 1 задачи | 0 потерь (3 обрыва) |
| Смок цикла до старта | был ли зелёный до автономии | НЕТ (главный провал v1 методики) |

**Про эскалации — метрику нельзя минимизировать.** Ноль технических вопросов
это успех: значит ТЗ полное, а исполнители не гадали. Ноль эскалаций —
не успех и не провал сам по себе: в простом проекте продуктовых развилок
может не быть вовсе, а в проекте с деньгами или чужими данными пустой
ESCALATIONS.md означает, что развилку прошли молча. Смотреть надо на третью
строку: сколько решений, менявших продукт, AI принял сам, а человек узнал
о них на приёмке. Вот её и держать на нуле.

Дополнительно фиксировать: активированные роли; какие пригодились/простояли;
сработавшие предсказания DECISIONS (у DocVault: BF02 предсказан за сутки);
движение по OPEN-QUESTIONS.md (какие вопросы закрыты этим проектом).
