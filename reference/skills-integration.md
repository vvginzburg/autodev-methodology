# Оригинальные навыки внутри AutoDev Codex

Профиль rc2 сохраняет исходные навыки и ресурсы из `dependencies/lock.json`.
Оригиналы неизменны; этот документ задаёт явную адаптацию их управления.
Принцип «AutoDev управляет, Superpowers помогают» унаследован из Claude.
Это не утверждение, что исходный SDD исполняется без изменений.

## Подготовка и применение

На машине исполнения нужен Python 3.9+ для двух локальных помощников.
Развернуть архивы в отдельную папку ресурсов проекта, не в каталог глобальных
навыков и не в исходник Claude:

```sh
python3 "<методика>/scripts/prepare_dependencies.py" --dest "<проект>/autodev/sources"
```

Команда проверяет хеши архивов, сохраняет обычные режимы файлов и директорий,
типы и цели ссылок. При повторении проверяет содержимое без перезаписи.
Повреждённую папку не ремонтировать поверх: сохранить, выяснить происхождение
изменений и подготовить другой путь. В env-check сохранить вывод, конечные
абсолютные пути, версию выпуска и хост. `sources/` — ресурсы, а не состояние
управляющего конвейера; оригинальные AGENTS/CLAUDE внутри архивов относятся
к разработке самих пакетов, их не подключать как правила продукта.

Каждая использующая навык роль получает в поручении: свою роль и бриф,
абсолютный путь оригинального SKILL.md, этот адаптер и контракт AutoDev.
Роль читает оригинал и нужные ему ресурсы, применяет правила своей строки
ниже и сообщает, что использует оригинал с адаптацией управления AutoDev.
Оговорку передавать вместе с каждым оригинальным prompt, включая повторное
ревью; чтение исходника для оценки не засчитывать как его применение.
Инструкции среды и пользователя имеют приоритет над всеми этими файлами.

Подключение не меняет обычные диалоги вне AutoDev. `using-superpowers`, его
bootstrap и SessionStart hooks глобально не активируются. Не создавать
ещё один workflow через `executing-plans`. Недоступность обязательного навыка
блокирует соответствующий этап полного профиля: пересказом его не заменять.

| Оригинал под `autodev/sources/` | Кто и когда применяет |
|---|---|
| `superpowers/skills/brainstorming/SKILL.md` | проектировщик, фаза 1 |
| `superpowers/skills/writing-plans/SKILL.md` | планировщик, перед исполнением |
| `superpowers/skills/subagent-driven-development/SKILL.md` | оркестратор, фазы 2–3 |
| `superpowers/skills/test-driven-development/SKILL.md` | исполнитель кодовой задачи |
| `superpowers/skills/systematic-debugging/SKILL.md` | исполнитель дефекта; исследование до исправления |
| `superpowers/skills/verification-before-completion/SKILL.md` | сдающая и принимающая роли перед утверждением готовности |
| `elements-of-style/skills/writing-clearly-and-concisely/SKILL.md` | автор/редактор документов человеку, вместе с полным справочником |

Для каждой строки раздельно фиксировать: источник доступен; оригинал загружен;
применение подтверждено событием и результатом. Одно объявление этого не доказывает.

## Обязательные переопределения в поручениях ролям

**Общее управление.** AutoDev хранит SPECIFICATION, PLAN, DECISIONS, ESCALATIONS,
STATUS и отчёты в `autodev/`. Канон принятия задачи — фаза 3. Исходные примеры
SDD с commit исполнителя, самостоятельным complete, пятью раундами, resume
прежнего исполнителя и parked-as-complete не применяются. Возврат получает
новая роль; после двух возвратов по одному спору — инженерный разбор по фазе 3.
Открытый обязательный критерий нельзя превратить в выполненный решением агента.

**brainstorming, включая spec-document-reviewer-prompt.** Один продуктовый
документ — SPECIFICATION AutoDev. Проверяющий читает его и исходные требования;
не требует второй spec в `docs/superpowers/specs`. Продуктовое согласование
сохраняется. Уже порученная реализация и технические детали внутри полномочий
не переоткрывают интервью. Visual companion в малом испытании не применяется;
если он выбран отдельно, его артефакты сохраняются до остановки сервера.

**writing-plans.** Один план — PLAN AutoDev. Каждый блок имеет заголовок
`### Task N: TNN — название`, внутри сохраняются checkbox и поля шаблона.
Оригинальный `scripts/task-brief` можно вызывать с явным OUTFILE в
`autodev/briefs/`: тогда он не создаёт SDD workspace. Перед отправкой
дополнить извлечённую задачу общими ограничениями, полномочиями, интерфейсами
и ссылками на канонические требования. Проверить полноту брифа; пустой
результат парсера не заменять догадкой. Коммиты из шагов плана выполняет
оркестратор после приёмки. SDD уже выбран; меню SDD/executing-plans не задаётся.

**SDD — оркестратор и implementer-prompt.** Свежая роль получает ограниченный
бриф без истории других исполнителей. Исполнитель сдаёт файлы, результаты
тестов и отчёт AutoDev; сам не коммитит и не меняет управляющие документы.
В поле исходного prompt «commits» указывает «не выполнял по контракту AutoDev».
Подтверждённые и запрошенные модели различаются; параметры берутся из живой
схемы инструментов. Правило оригинала об обязательном выборе другой модели
или её автоматическом повышении не переопределяет ограничения среды и
пользовательский выбор. Ожидания — по правилам текущей среды.

Оригинальный `scripts/sdd-workspace` и его автоматическое восстановление по
ledger не запускаются. Проекция ledger, если полезна, хранится в
`autodev/sdd-progress.md`, содержит ID задачи, ссылку на PLAN, отчёт ревью и
принятый commit. Она не определяет приёмку. Восстановление сверяет документы,
Git и доказательства; одиночный complete не разрешает пропустить задачу.
Временные брифы и пакеты ревью именуются ID задачи и раундом; не удалять их
как scratch до сохранения доказательств. Отдельный второй план запрещён.

**task-reviewer-prompt, re-review-prompt, requesting-code-review/code-reviewer.**
До коммита проверяется рабочий кандидат по [review-candidate.md](review-candidate.md).
Это замена исходного `scripts/review-package` и всех fallback-команд BASE..HEAD
для незакоммиченной задачи. Ревьюер читает файлы кандидата, требования и код,
включая новые файлы. Следующий раунд сравнивает два manifest/объекта, даже
если HEAD прежний. Свои выводы привязывает к ID кандидата; baseline commit
не выдаёт за commit реализации. Замечания по плану направляет оркестратору.

Обзор кода и независимый запуск проверок — разные действия. Ревьюер AutoDev
может выполнять обе функции и явно разделяет их в отчёте. Запрет SDD на
повторный suite не отменяет необходимую независимую приёмку. Без изменений
или нерешённых рисков весь suite повторять не нужно; чужой запуск нельзя
называть своим. Если проверка создала новые файлы в scope, разобрать их,
обновить явные исключения и заново зафиксировать кандидат перед приёмкой.

**using-git-worktrees.** Можно проверить уже существующую чистую изолированную
копию. При невозможной изоляции не применять fallback к небезопасной общей
папке; сохранить работу и обозначить препятствие. Исходные красные тесты
разбирает инженерная команда. Изменение .gitignore и коммиты выполняет только
уполномоченная роль; чужие файлы и индекс не очищать.

**systematic-debugging и test-driven-development.** После трёх неудачных
исправлений — независимый инженерный разбор причины/архитектуры до новой
попытки. Технические трудности и обоснованные исключения TDD адресуются
оркестратору в пределах полномочий. Для документов red-тест не требуется;
для изменения поведения нужен проверяемый критерий, воспроизведение и
регрессия. Пропуск реального тестирования и фиктивные тесты не разрешаются.
Владельцу идёт только необходимое решение по принципу 14.

**verification-before-completion и finishing-a-development-branch.** Проверки
подтверждают сдаваемый снимок, а не произвольный прежний HEAD. После общего
независимого обзора — приёмка и ретро AutoDev. Способ доставки задаётся
профилем/полномочиями: в локальном испытании выбран keep, без меню merge/push.
Артефакты сохраняются; завершение не разрешает автоматически удалить их.
Для итогового обзора уже закоммиченного диапазона допустим оригинальный
`scripts/review-package PLAN MERGE_BASE HEAD OUTFILE`: четвёртый аргумент
обязателен, путь в `autodev/reviews/`, чтобы не запускать sdd-workspace.
Незакоммиченные изменения этот диапазон не покрывает; для них нужен кандидат.

**Elements of Style.** Используется полный оригинальный справочник. Для
русского текста применяются подходящие правила ясности, без переноса
английской грамматики. Проверить сохранение чисел, ограничений и смысла.

## Профили инструментов

Ядро: Codex с независимыми агентами, Git, Python 3.9+ и навыки выше. MCP
назначаются по реальной задаче. Context7 требуется при незнакомом стеке;
подмена его другим источником отмечается как изменение профиля, а не успешный
вызов Context7. GitHub/gh нужны для согласованной работы с remote, не для
локального прогона.

Веб-приёмка «Заявки на ремонт»: `@upstash/context7-mcp@4.0.5`, `shadcn@4.21.0`,
`@playwright/mcp@0.0.80`. Эти кандидаты закреплены в lock.json; совместимость
ещё проверяется. На машине исполнения инфраструктура ставит их в отдельную
папку с lockfile всех зависимостей и браузером нужной версии. Обнаружение
сервера и реальный MCP-вызов проверяются отдельно. Не применять `npx latest`
как установочную инструкцию. Serena и episodic-memory не нужны этому примеру.
