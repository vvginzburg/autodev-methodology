# AutoDev — методика автономной агентной разработки

*Документ для человека. Прочитайте его целиком один раз — дальше методика
работает сама, а этот файл останется справочником. Для AI точка входа — SKILL.md.*

## Какую проблему это решает

Обычная работа с AI-помощником при разработке выглядит так: вы сидите рядом,
отвечаете на вопросы, подтверждаете действия, подталкиваете, когда он
останавливается. Получается «бебиситтинг»: AI пишет код, но ваше время
всё равно занято целиком.

AutoDev переворачивает это. Вся ваша вовлечённость сжимается в три коротких
окна, между которыми AI работает один — часами, ночью, без единого вопроса:

```
 ВЫ                AI                                   ВЫ            ВЫ
 ├─ проектируете ─► строит автономно ────────────────► приёмка ───► ретро
 │  (~2-4 часа)     (часы/сутки, 0 вопросов к вам)      (~1 час)     (~1 час)
```

На проекте-первоисточнике (DocVault: приложение-сканер документов для
iPhone/Mac с синхронизацией) это дало: 16 задач + 4 багфикса за ~2 суток,
76 автотестов на двух платформах, ноль вопросов во время разработки,
~5 часов человеческого времени суммарно.

## Как это работает — рассказ

**Сначала вы долго разговариваете.** AI задаёт вопросы по одному, простым
языком, с примерами: что за продукт, как выглядит каждый экран, что считать
«хорошо» (обязательно с числом: не «файл поменьше», а «≤700 КБ на страницу»),
что НЕ входит в первую версию. Каждый ваш ответ фиксируется. Из этого
рождаются три документа: **RRR.md** — подробное ТЗ с критериями приёмки,
**PLAN.md** — все задачи волнами с зависимостями, и **CLAUDE.md** — правила,
по которым будет жить автономная стройка. Это самая важная инвестиция:
час качественного проектирования экономит ночь переделок.

**Потом проверяется, что автономия физически возможна.** Прежде чем вы
уйдёте, прогоняется «смок-тест цикла»: крошечная задача-пустышка проходит
весь конвейер (агент пишет → другой агент проверяет → коммит в git) без
единого вопроса к вам. Если что-то спотыкается — логин, права, засыпающий
компьютер — это чинится СЕЙЧАС, при вас, а не в три часа ночи. (Этот этап
появился кровью: в первом запуске DocVault цикл сжёг 12 холостых попыток
из-за незалогиненного инструмента.)

**Дальше — конвейер без вас.** На каждую задачу из плана создаётся **свежий
агент-исполнитель**: он пишет сначала тест (который падает), потом код
(тест зеленеет) — это называется TDD и защищает от «вроде работает».
Его результат принимает **отдельный агент-ревьюер**, который этот код
не писал: он заново читает требования, сам перезапускает все тесты
и придирается. Это не формальность — на DocVault ревьюеры поймали
потенциальную потерю данных и несколько краевых случаев, которые
исполнители честно не видели (кто писал — тот верит своему коду).
Принятая задача немедленно коммитится в git — поэтому любой обрыв
(лимит подписки, закрытая крышка, сбой) теряет максимум одну задачу.

**Вопросы, на которые нет ответа в ТЗ, не останавливают работу.** Агент
принимает разумное инженерное решение и записывает его в **DECISIONS.md**:
дата, вопрос, решение, почему. Вы потом просматриваете этот файл за десять
минут — это все точки, где AI решал за вас. Самая ценная разновидность
записей — предсказания: на DocVault одна из них предсказала баг за сутки
до того, как он проявился, вместе с готовым лечением.

**Ваше возвращение — приёмка.** К этому моменту всё программно проверяемое
уже проверено сотнями прогонов (даже камера — через «фейковую» реализацию,
подсовывающую тестовые документы). Вам остаётся то, что существует только
в физическом мире: навести настоящую камеру на настоящий паспорт, увидеть
документ на втором устройстве, пощёлкать руками. Найдёте баги — это
нормально и ожидаемо (на DocVault их было 4, все строго в «физической»
зоне): каждый чинится тем же конвейером, причём сначала баг воспроизводится
автотестом, чтобы больше никогда не вернуться.

**И финал — ретро.** Полчаса разговора: что в методике сработало, что
скрипело. Выводы коммитятся в саму методику (в этот репозиторий) — так она
умнеет от проекта к проекту. Это не пожелание, а обязательная фаза:
методика без петли обратной связи мертва.

## Команда агентов

Постоянное ядро — трое:

| Роль | Метафора | Главное правило |
|---|---|---|
| Оркестратор | прораб | держит план, раздаёт задачи, сам код не пишет |
| Исполнитель | рабочий | свежий на каждую задачу, работает через TDD |
| Ревьюер | приёмщик | никогда не тот, кто писал; верит фактам, не отчётам |

Под задачу масштабирование — «полка» из семи дополнительных ролей
(постановщик задач, интеграционный ревьюер, инфра-инженер, тест-инженер,
релиз-инженер, технический писатель, канцелярия) — они описаны заранее
и включаются либо по очевидным признакам проекта (несколько платформ →
интеграционный ревьюер), либо по «правилу второго раза»: оркестратор
делает какую-то работу руками второй раз подряд → выделяется роль.
Подробно: roles/core.md и roles/catalog.md.

Почему агенты «свежие», а не один постоянный: у постоянного контекст растёт
с каждой задачей и оплачивается заново при каждом шаге (в итоге — дороже),
а главное — он «привыкает» к своим решениям. Незамыленный глаз ревьюера —
источник большинства находок. Общее знание живёт не в головах агентов,
а в файлах: RRR, DECISIONS, CLAUDE.md, справочник граблей.

## Что нужно для работы (зависимости)

**Обязательно:**
- **Claude Code** (Desktop-приложение или CLI) — среда, в которой всё живёт;
- **git** — память процесса (на Mac идёт в комплекте с Xcode/CLT);
- **плагин Superpowers** — кирпичи процесса, на которые методика ссылается:
  brainstorming (проектирование), writing-plans (план),
  subagent-driven-development (конвейер), test-driven-development (TDD),
  verification-before-completion (финальная проверка);
- **gh** (GitHub CLI, авторизованный) — если нужен облачный git и установка
  на устройства через репозитории.

**По типу проекта** (пример — Apple-платформы): Xcode + симуляторы, XcodeGen,
платный Apple Developer Program для iCloud/устройств (активация до 48 ч —
оформлять на фазе проектирования!).

**Проверять руками ничего не нужно**: первая фаза любого проекта — «Фаза 0»
(phases/00-environment.md), где AI сам проверяет наличие всего из этого
списка, говорит, чего не хватает, и ставит недостающее (или даёт вам
одну команду/кнопку там, где ставить должен человек).

## Как начать

1. Установите методику (см. «Установка» ниже) — или она уже стоит,
   если вы читаете это на своём компьютере.
2. В любой сессии Claude Code скажите: **«новый проект по методике autodev»**.
3. Дальше вас поведут: фаза 0 проверит окружение, фаза 1 — это разговор
   с вами, фаза 2 закончится смок-тестом, после которого можно уходить.

## Установка на чистый компьютер

```
git clone https://github.com/vvginzburg/autodev-methodology.git ~/.claude/skills/autodev
```
— всё; скил станет виден каждой сессии Claude Code. Недостающие зависимости
поставит фаза 0 первого же проекта.

## Панель применения

Публичная панель KPI всех отчитавшихся проектов:
**https://vvginzburg.github.io/autodev-methodology/** — данные добровольно
присылаются на ретро (фаза 5) Pull Request'ом в папку metrics/; страница
читает их напрямую из репозитория. Скачивания и интерес — Insights → Traffic
и звёзды/форки на GitHub.

## Как методика развивается

Каждый проект заканчивается ретро с коммитом сюда (или явным «изменений
нет»). Развитие меряется числами, а не ощущениями — reference/metrics.md
хранит метрики и базовую линию: доля задач, принятых с первого раза;
баги приёмки на 10 задач; минуты человека; токены на задачу. Версия N+1
обязана улучшать эти числа.

## Карта репозитория

- **SKILL.md** — вход для AI (краткий, токен-экономный)
- **README.md** — этот документ, вход для человека
- **phases/00–05** — подробные инструкции каждой фазы
- **roles/** — должностные инструкции агентов
- **templates/** — заготовки всех файлов проекта
- **reference/** — грабли окружения, бюджет токенов, метрики, разобранный кейс DocVault
- **CHANGELOG.md** — история версий методики
