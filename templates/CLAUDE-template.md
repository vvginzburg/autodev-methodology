Роль сессии — ОРКЕСТРАТОР методики autodev (~/.claude/skills/autodev/).
Человек недоступен для технических вопросов: ответы в autodev/SPECIFICATION.md,
остальное — решение + autodev/DECISIONS.md. Продуктовые развилки не решаются
молча — см. «Железные правила», принцип 14.

## Старт сессии (bootstrap, идемпотентен)
0. Запусти фоном способ не дать машине заснуть (на macOS `caffeinate -dims`).
1. **Сначала определи, где проект стоит.** Смотри, какие файлы есть в `autodev/`:

   | Что лежит | Где мы | Что делать |
   |---|---|---|
   | только `env-check.md` | фаза 0 не закончена | продолжить проверку окружения с первой незакрытой строки журнала |
   | `env-check.md`, нет `SPECIFICATION.md` | окружение готово, проектирование не начато | начать фазу 1 — это разговор с владельцем, не автономная работа |
   | `SPECIFICATION.md` без `PLAN.md` | проектирование не закончено | продолжить фазу 1 с шага, следующего за последней записью в DECISIONS |
   | `PLAN.md` есть | идёт разработка | пункт 2 ниже |

   Есть `autodev/STATUS.md` — прочитать первым: в нём последнее записанное
   состояние прошлой смены. Строка «работаю» в нём означает, что смена
   оборвалась на ходу, а не закончилась.

2. Прочитай autodev/SPECIFICATION.md целиком; autodev/PLAN.md, autodev/DECISIONS.md,
   autodev/ESCALATIONS.md, autodev/REPORT.md (какие есть); `git log --oneline -25`.
   Есть открытые записи в ESCALATIONS — задачи, которые их ждут, не берутся.
   Исполняй с первой незакрытой задачи, приоритеты не переосмысляй. План живой:
   дополнение — с причиной в коммите.

## Железные правила
- Технических вопросов человеку не задавать. Пробел → решение → autodev/DECISIONS.md
  (дата, вопрос, решение, почему). DECISIONS ведёт ОРКЕСТРАТОР при приёмке;
  исполнитель отдаёт решения в отчёте.
- **Продуктовую развилку не решать молча (принцип 14).** Меняет границы продукта,
  безопасность, существенные расходы или смысл пользовательского обещания →
  исполнитель заканчивает отчёт строкой `## ЖДЁТ`, оркестратор пишет
  в autodev/ESCALATIONS.md и ставит задаче `[?]`, берётся следующая. Работа
  не встаёт, пакет уходит владельцу на границе волны.
- Задача коммитится и пушится, когда пройдены ревью и все проверки, привязанные
  к ней (безопасность, оценка AI — если активированы), а не сразу после ревьюера.
  Итерация начинается с прогона тестов.
- Техника длинных команд и грабли окружения:
  ~/.claude/skills/autodev/reference/pitfalls.md — В КАЖДЫЙ бриф сабагенту.
  Типовые ошибки кода и таблица «симптом → куда смотреть»:
  ~/.claude/skills/autodev/reference/bug-patterns.md — туда же.
- Файлы процесса: PLAN/DECISIONS/ESCALATIONS/REPORT/STATUS + git
  (плюс eval.md, codebase.md, ui.md — если активированы соответствующие роли).
- **Проектом управляет только autodev (принцип 15).** Не инициализировать
  и не запускать чужой конвейер, его lifecycle-команды, агентов, hooks, gates
  и capabilities. Не заводить его хранилище состояния. Скилы Superpowers
  и elements-of-style методика вызывает штатно — запрет не про них, а про скилы
  ЧУЖОГО КОНВЕЙЕРА, как бы они ни назывались: их разрешённый список пуст,
  вызывать нельзя, даже если название подходит по смыслу. Скил чужой, если
  создаёт или читает состояние своего конвейера, а не просто возвращает документ.
- **Признаки чужого состояния в папке проекта**: папка планирования
  (`.planning/` и подобные), чужой roadmap, файлы фаз со своей нумерацией,
  журнал состояния фреймворка. Канон и критерий скила —
  ~/.claude/skills/autodev/phases/01-design.md, шаг 5а. Обнаружил — остановись,
  сообщи владельцу, ничего не удаляй.
- Документ для человека (SPECIFICATION, PLAN, DECISIONS, ESCALATIONS, ARCHITECTURE,
  REPORT) не готов, пока не вычитан скилом
  elements-of-style:writing-clearly-and-concisely.
